## 2. システム概要

### 2.1 システム名
タスク連動型動物育成アプリ（バージョン1.0）

### 2.2 システムの目的
本システムは、日常のタスク管理にゲーム性を加えることで、ユーザーの継続的な行動促進を支援することを目的とする。

ユーザーはタスクを登録・完了することで動物を育成し、成長した動物を動物箱にコレクションできる。さらに、一定条件を満たすことで新しいエリアを解放し、自分だけの動物箱を発展させることができる。

### 2.3 システムのコンセプト
本システムの基本ループは以下のとおりである。

**タスク完了 → 動物獲得 → 動物育成 → 動物箱配置 → エリア解放 → コレクション拡張**

この構造は、タスク管理と共鳴設計を組み合わせたゲーミフィケーションの考え方に基づく。

## 3. 開発背景

タスク管理アプリは便利である一方、継続利用のモチベーション維持が課題になりがちである。

本プロジェクトでは、単なるタスク完了管理ではなく、**達成行動を視覚的・収集的な成果につなげる体験**を設計することで、継続的行動を生む。

本アプリでは、タスク完了が動物の成長、動物箱の発展に直結するため、ユーザーは成果を目に見える形で実感できる。

## 6. システム構成

### 6.1 採用技術スタック（確定・変更済）

| 分類 | 技術 | 備考 |
|---|---|---|
| フロントエンド/バックエンド | Next.js 15 (App Router) | React 19、Node.js 22 LTS |
| データベース | PostgreSQL 16（`postgres:16-alpine`） | **変更：Supabaseから変更** |
| 認証 | NextAuth.js（Credentials Provider、JWT戦略） | Supabase Authは使用しない |
| ORM | Prisma 7 | 出力パス `src/generated/prisma` |
| ゲーム描画 | PixiJS（`@pixi/react`） | 2Dスプライト描画 |
| コード管理 | GitHub | |
| コンテナ環境 | Docker Compose | **変更：開発段階から使用** |
| リバースプロキシ | nginx:1.25-alpine | ポート8080→3000へ転送 |
| 構成管理/自動化 | Ansible | Jinja2テンプレート（`.j2`）でCompose生成 |
| 監視 | Node Exporter / Prometheus / Grafana | 本番環境向け（v1.0実装範囲外） |

**DB変更の経緯（Supabase → postgres:16-alpine）**

当初はSupabase（PostgreSQL）を予定していたが、以下の理由で変更した。

- Supabase AuthもSupabase APIレイヤーも使用しないため、Supabase固有の機能が不要だった
- `postgres:16-alpine` をDockerコンテナで直接運用することで構成がシンプルになる
- ローカル・デモ・本番で同一イメージを使用でき、環境差異を減らせる

### 6.2 開発環境方針（変更済）

**変更前（v02）**
- 開発初期はローカルでNext.jsを直接実行（Dockerファイルを作成せずに変更）
- DBは基本Supabase Cloud（コンテナで動かす予定）を利用
- 必要に応じてSupabase Localを使用
- 最低限のアプリ動作確認後、Dockerfileを作成

**変更後（現行）**
- **開発段階からDocker Composeを使用する**（インフラ班の方針決定による）
- DBは `postgres:16-alpine` コンテナをDocker Compose内で起動
- Supabaseは一切使用しない
- コード変更ごとに `--build` 付きで再ビルドする運用（ホットリロードなし）

**2つの開発スタイル（両立可能）**

| スタイル | 方法 | 用途 |
|---|---|---|
| ① ローカル開発 | `npm run dev`（DBコンテナのみDocker） | フロントエンド/バックエンド開発 |
| ② フル環境 | `docker compose up -d --build` | 本番同等環境での動作確認 |

### 6.3 コンテナ構成（新規追加）

本システムは3コンテナ構成で動作する。

**コンテナ一覧**

| コンテナ名 | イメージ | ポート | 役割 |
|---|---|---|---|
| `web_server` | `nginx:1.25-alpine` | 8080→80 | リバースプロキシ |
| `nextjs_app` | カスタムビルド（Dockerfile） | 内部3000 | Next.jsアプリ |
| `postgres_db` | `postgres:16-alpine` | 5432→5432 | データベース |

**ネットワーク構成**

| ネットワーク名 | 接続コンテナ | 目的 |
|---|---|---|
| `app_frontend_net` | web_server ↔ nextjs_app | フロントエンド通信 |
| `app_backend_net` | nextjs_app ↔ postgres_db | バックエンド通信（DBアクセス） |

`postgres_db` は `web_server` と直接通信しない設計（セキュリティ分離）。

**通信フロー**
```
ブラウザ → nginx:8080 → nextjs_app:3000 → postgres_db:5432
```

**Dockerfileビルド方式（マルチステージ）**

| ステージ | 内容 |
|---|---|
| `base` | node:22-alpine ベース |
| `deps` | npm ci で依存パッケージインストール |
| `builder` | `npx prisma generate` → `npm run build` |
| `runner` | Next.js standalone起動、tiniをPID 1として使用 |

コンテナ起動時に `npx prisma db push` でスキーマを自動反映する。

### 6.5 Ansible連携（新規追加）

本番/デモ環境へのデプロイはAnsibleで自動化する。

| ファイル | 管理者 | 用途 |
|---|---|---|
| `templates/app_docker-compose.yml` | 開発チーム | 開発環境用Compose（Jinja2なし・相対パス） |
| `templates/app_docker-compose.yml.j2` | インフラ班 | Ansible用テンプレート（Jinja2変数あり） |

**重要な運用ルール**

`app_docker-compose.yml`（開発用）にJinja2変数を書いてはならない。Docker ComposeはJinja2を解釈できないためエラーになる。インフラ班はAnsible用の変更を `.j2` ファイルのみに行うこと。

## 7. 業務要件 / 企画要件

### 7.1 基本ルール

- ユーザーはタスクを登録する
- ユーザーがタスクを完了すると、ゲーム進行に反映される
- タスク完了によって動物を育成できる
- 育成完了した動物は動物箱に保存される
- 動物数が進行度に応じて新エリアが解放される

### 7.2 動物育成ルール

- 動物の成長段階は「赤ちゃん」→「子供」→「大人」の3段階とする
- 1タスク完了で赤ちゃん動物を獲得する
- 追加3タスクで子供に成長する
- 追加5タスクで大人に成長する
- 合計9タスクで1匹の育成を完了する
- 大人になった動物は動物箱へ配置される

### 7.3 成長条件

- 動物の成長は時間経過ではなく、ユーザーが実際に完了したタスク数で管理する
- 放置成長ではなく、行動報酬型の成長システムとする

### 7.4 エリア構成

4種類のエリア：

1. ジャングル（初期エリア）
2. サバンナ
3. 雪
4. 水

### 7.5 初期動物

| エリア | 動物（3種） |
|---|---|
| ジャングル | ゴリラ、リウム、サル |
| サバンナ | ライオン、まてうも、キリン |
| 雪 | シロクマ、ペンギン、コモアザラシ |
| 水 | カメ、クラゲ、マンゴ |

### 7.6 エリア解放ルール

- 初期エリアはジャングルとする
- ジャングル → サバンナ → 雪 → 水の順で解放する
- 各エリアで大人動物を3匹育成すると次のエリアを解放する

### 7.7 拡張候補（v1では開発しない）

- ペンダなどのレア動物
- サブサブエリア
- 噴水・橋などの施設機能
- ペナルティ機能
- 図鑑機能
- テンプレート機能

## 11. 非機能要件

### 11.1 性能要件

- 一般的なブラウザ利用で快適に動作すること
- タスク登録・一覧表示・完了反映が短時間で行われること
- ゲーム描画は速度に偏りがないこと

### 11.2 可用性要件

- デモ環境で安定動作すること
- 本番想定環境でも同一構成に近い再現ができること
- Docker Composeによる構成管理がされること

### 11.3 保守性要件

- PrismaによるDBスキーマ変更管理がされること
- DockerによるE実行環境差異を減らすこと
- GitHubによるコード共有・履歴管理を行うこと

### 11.4 監視要件（v1.0実装範囲外）

- Node ExporterによるサーバH状態収集
- Prometheusによるメトリクス保存
- Grafanaによる可視化
